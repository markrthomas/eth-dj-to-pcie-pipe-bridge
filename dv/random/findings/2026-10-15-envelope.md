## 4. Overload class (D9 contract) — backlog, not implemented
A deliberately out-of-envelope job class cannot be added without touching the fixed-scenario checks: every fixed scenario and the `rand` scenario treat `tuser[0]` as an error (`frame aborted`) and a frame that never arrives ends in `scenario op timeout`, so any overloaded run fails those checks by design. The D9 contract (flagged-or-exact frames, in order; at least one frame aborted) **is already asserted in every non-FC job** by scenario 6 `rxovf`, which forces `sink 4 %` itself (`bridge_bfm.h` scenario 6 + the `res_.err_frames == 0` check). What is missing is a randomised overload stimulus (variable sink/mac_gap/lengths) with that same checker: needs a new `+overload` scenario reusing the rxovf checker; backlog.

## 6. Finding-C observation: a whole frame can vanish without `tuser[0]`
Question for the owner: does it match the intended D9 behaviour?
- Mechanism (rtl read, not changed): when the **sof flit** of a frame is dropped on overflow (`rx_ingress`: `drop_now`, counted in RXCNT0 `dropped_flits`), `flit_gap` is set on the **next** flit delivered. In `rx_deframer` `abort = flit_valid && fstart && in_frame_q && (flit_gap || hsof || bad)` — it requires `in_frame_q`. If the previous frame has completed (its eof flit was accepted), the deframer is idle, so the continuation flits of the damaged frame hit `drop = !in_frame_q && (bad || !hsof)` (orphan: dropped, counted RXCNT1 bad/orphan). Result: nothing is emitted for that frame, in particular no `tlast` beat with `tuser[0]`; the gap marker is discarded with the dropped orphan. A single-flit frame (sof+eof) dropped entirely leaves only RXCNT0.
- D9 text (`docs/OPEN_DECISIONS.md` D9): "never deliver a silently corrupted frame ... marks the next flit (`flit_gap`); ... the deframer **aborts the frame in progress**" and "Orphan continuation flits (no `sof`, not in a frame) are dropped (RXCNT1 bad/orphan)". The behaviour above is exactly what that text specifies: abort applies only to a frame in progress, and orphan drops are specified as silent in-band (counted only). It also satisfies the stated goal (no corrupted frame is delivered; the loss is a missing frame, visible only in RXCNT0/RXCNT1).
- Gap in the spec'd intent (for the owner to decide): the *in-band* indication (`tuser[0]`) exists only for frames that start. A frame lost from its first flit is indistinguishable downstream from a frame that was never sent; only the CSR counters show it. The title of D9 ("drop + abort the damaged frame") may suggest more than the text delivers. Options if the owner wants it: emit a 1-byte aborted beat when an orphan arrives with `flit_gap` set and `!in_frame` (one added case in the deframer + golden/TB update). Not done; not a bug under the current text.
- In the finding-C repro this made the Ethernet sink count never reach `OP_WAIT_RX n`; with the runner now keeping non-FC jobs at sink >= 70 this no longer occurs in random runs.

## E1 resolution (rr-dbg-e1)
- Corpus id is `rr0004` (the entry above says rr0001; that id belongs to the x4 loop entry).
- Root cause: **golden/BFM bug, DUT correct.** In `scenarios.ctl_plan` / `bridge_bfm.h gen_ctl_plan_` the "rewrite the held CTRL value" item emitted a CTRL write but did not call `CtlSim.ctrl_wr`. When the held value requests P0s (e.g. 0x31), `bridge_rf` sets ERR[2] again for that write (D19.3: once per CTRL write), so after an ERR clear the exact read-back (want 0) was wrong. Trace: plan op CTRL=0x31, ERR W1C 0xf, CTRL=0x31 (rewrite), settle, ERR read -> got 4.
- Fix: golden and BFM mirror call `ctrl_wr` for that item (no check weakened, RTL unchanged). Before: rr0004 2 errors; after: pass; 3 x N=300 batches (712 jobs with rand_ctl>0 of 900) 0 failing.
